# `modules/data` — Aiven MySQL (external) + Secrets Manager

Group-owned platform module. Writes an Aiven MySQL service's connection
details into the Secrets Manager credential envelope `modules/service`
resolves at boot.

> **2026-08-18 trainer update:** RDS isn't on LocalStack's free Hobby tier, so
> the managed database moved to [Aiven for MySQL](https://aiven.io) — a real
> external managed MySQL, free forever, provisioned by hand (not by this
> module — see "Setting up Aiven" below). Everything downstream of the
> database — Secrets Manager, EC2, the scanning gates — stays exactly as the
> brief describes. Only where the database lives changed. ECR is also gone
> from the assignment (not on the free tier either); irrelevant to this
> module either way, since it never touched a registry.

## What it creates

| Resource | Purpose |
|---|---|
| `aws_secretsmanager_secret` / `_version` | The credential envelope `modules/service` reads at boot |

That's it. This module used to also provision an `aws_db_instance`, its
subnet group, and its security group — see git history (the PR that merged
before this trainer update) for the RDS-era version. None of that applies to
an external service with its own credentials and its own network boundary.

## Setting up Aiven (do this once, per person, ~5 minutes)

1. Sign up at [aiven.io](https://aiven.io) — free personal account, no card.
2. Create a new service → MySQL → **Free plan** → create. Give it a minute or
   two to finish starting.
3. Open the service page, copy: host, port, user (`avnadmin`), password.
   Download the CA certificate too (Aiven requires TLS).
4. Put host/port/username/password into your repo's GitHub Actions secrets
   *and* your local environment as `TF_VAR_aiven_host`, `TF_VAR_aiven_port`,
   `TF_VAR_aiven_username`, `TF_VAR_aiven_password`. **Never commit them.**
5. This module writes them into Secrets Manager; your app reads them at boot,
   exactly as the brief describes.

One free MySQL per Aiven account — use your own, don't share one. The free
service sleeps when idle; open it or hit it once before you start working.
Free-tier limits (1 GB storage, 76 connections) are plenty for this lab.

## Inputs

| Name | Default | Notes |
|---|---|---|
| `name_prefix` | `devops-g1-ls` | Name/tag prefix |
| `db_name` | `capacity_lab` | Database name on the Aiven service — create it yourself, or use their `defaultdb` |
| `secret_name` | `regional-health/db` | Secrets Manager name |
| `aiven_host` | — | **No default** — your Aiven service hostname |
| `aiven_port` | — | **No default** — Aiven assigns this per-service |
| `aiven_username` | `avnadmin` | Aiven's free-tier admin username |
| `aiven_password` | — | **No default, `sensitive = true`** — never a tfvars value |
| `recovery_window_in_days` | `0` | Lab default (immediate secret purge on delete); override to `7`-`30` in a real production root |

`db_name` and `secret_name` are the frozen contract in
[`docs/MODULE-CONTRACTS.md`](../../../docs/MODULE-CONTRACTS.md) (the RDS-only
inputs the contract used to list — `db_username`, `instance_class`,
`allocated_storage`, `engine_version` — are gone with the RDS resources that
used them; contract doc updated alongside this module).

## Outputs

`db_endpoint`, `db_port`, `secret_arn`, `secret_name` — same names, same
meanings `modules/service` already expects. `db_endpoint` is now the Aiven
hostname passed straight through, no rewrite involved.

## Credential handling (C3)

`aiven_password` is a `sensitive = true` variable with no default — it must
come from `TF_VAR_aiven_password`, sourced from a GitHub Actions repo secret
in CI and your local shell for manual runs, the same discipline
`LOCALSTACK_AUTH_TOKEN` already uses. It is never generated by this module
(Aiven generates it), never has a default, and never appears in a tfvars
file. The only place it exists outside the secret itself is Terraform state,
which is why remote state (S3 + DynamoDB lock) has to stay access-controlled.

Secret envelope JSON keys, exactly (frozen by the contract, unchanged by the
Aiven switch): `engine`, `username`, `password`, `host`, `port`, `dbname`.
`modules/service` passes only `secret_arn` + `db_endpoint`/`db_port` into
user-data — the app calls `GetSecretValue` itself at boot. No plaintext
credential in git, image, or logged output.

**TLS / CA certificate**: Aiven requires TLS and gives you a CA cert to
verify it. That cert is *not* secret (it's a public root cert), so it
deliberately doesn't go through this module or Secrets Manager. **Resolved:**
`modules/service` now takes it as a plain non-sensitive variable
(`db_ca_cert`) and writes it to `/etc/app/db-ca.pem` on the instance,
exporting `DB_CA_CERT_PATH` for the app to pick up — see that module's
README. This module still deliberately has no opinion on the cert; it's
entirely `modules/service`'s concern, as designed.

## Testing

- `tofu fmt` + `tofu validate` clean.
- The TLS handshake itself is confirmed working end-to-end against a real
  Aiven service (`mysql --ssl-ca=<the same cert> --ssl-verify-server-cert`
  reaches MySQL's own auth stage, i.e. TLS negotiation succeeds) — but the
  full app-boot path (EC2 instance → app → `GetSecretValue` → TLS to Aiven,
  all inside a LocalStack-emulated instance) is **still blocked** by the
  separately-documented LocalStack EC2 limitations in the rehosted service
  repos' `evidence/01-iac/README.md` (Docker-backed AMI discovery, ELBv2
  license) — not something this module or the `db_ca_cert` fix can resolve
  on its own.
